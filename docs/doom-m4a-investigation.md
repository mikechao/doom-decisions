## Chosen architecture

Create **`app/`**, with vanilla JavaScript, Vite, an app-local manifest and lockfile, exact `openai@7.32.0`, and an exact compatible Vite version selected and verified during M4-B. Record the actual Node/npm versions. Bundle the SDK into static output with relative deployment URLs; preserve historical `experiments/` unchanged.

The architecture stays static-only and browser-direct: no Doom Decisions backend, proxy, database, or server-side controller. BYOK remains prototype scope. Only the Worker instantiates WASM and advances real Doom. Snapshot, Canvas capture, render, API waiting, and idle must not advance gameplay. Each fresh initialized/prepared instance requires exactly one explicit neutral first tic. M3-E3 fixed each model action at six tics; M4 will eventually let the **user** choose 1–20 tics while the model chooses only an action. No autoplay is in scope.

| Tool option | Decision |
| --- | --- |
| Vanilla JS + Vite | Chosen: small app-local build setup, locked dependencies, bundled SDK, and a raw-source path for the proven Worker. Exact Vite compatibility is not yet verified. |
| Vanilla TS + Vite + TypeScript 7 | Optional later, not an M4 prerequisite. Typed messages/SDK narrowing could help maintenance, but add compiler/configuration work with little compiler-speed benefit at this prototype size. Browser bundling and TypeScript type-checking are separate: Vite's TS transformation does not establish type correctness; a TS 7 checking step would still be needed. No TS 7 compatibility check was performed. |
| No bundler | Feasible with an independent app-local SDK installation and a reproducible copy of its published module tree/notices into static output. M3-E2 proves the unbundled delivery approach, but this adds a packaging/copy step and a larger runtime module graph. It is less convenient for the requested build artifact. |

**Corrected asset decision:** automatically deliver/load the generated, verified `doom.wasm` from the deployed app base. The user must not select or upload WASM. Use Git-ignored generated staging rather than a manually copied binary as authoritative source. `app/public/doom.wasm` remains one proposed staging location, not an existing pipeline: M4-B must ignore it, replace/verify it for each successful handoff, and prevent stale or checked-in copies from entering output. Keep the IWAD user-selected for now; use the pinned Freedoom Phase 1 IWAD for the packaging smoke. Selecting arbitrary WADs is not established by the accepted checks. ## Unified shell build amendment

**Agreed responsibilities:** a root `build.sh` will provide thin orchestration, propagate failures, hand off/stage verified WASM, and invoke the frontend build. No new build framework or task-runner dependency is needed. `scripts/build_doom.py` remains the engine build entrypoint, admitting inputs and invoking the vendored Make graph under `engine/doom/` and static inspector; it must not absorb frontend orchestration. Make retains engine recipes/flags/transforms. Vite builds static frontend assets and includes the generated WASM in self-contained `app/dist/`, with no IWAD. No root `build.sh` exists at this amendment's inspection; its implementation is not authorized here.

**Observed engine interface and constraints:**

- [Python CLI, lines 307–320](../scripts/build_doom.py#L307-L320) requires `--profile` (`upstream-shareware` or `controlled-title`) and `--out`; accepts `--jobs` 1–2 (default 2), `--timeout` 1–120 seconds (default 120), existing tool paths via `--wasi-sdk`, `--binaryen-bin`, and `--node`, and the controlled-profile-only `--without-a1-fixtures` option. Defaults point to local `tools/wasi-sdk-24.0` and `tools/binaryen-119/bin`.
- [Admission, lines 195–231](../scripts/build_doom.py#L195-L231) requires Python 3.14.4, POSIX process groups, GNU Make 3.81 at `/usr/bin/make`, Clang/LLD 18.1.2 from WASI SDK 24, Binaryen 119 tools, Node exactly 22.20.0, SDK sysroot/builtins, and at least 512 MiB free disk. Output must be a **new**, ignored directory beneath `engine/doom/build/`, without symlink ancestry; the wrapper cannot output directly into `app/dist/` or overwrite an existing engine output.
- `controlled-title` forbids embedded-WAD arguments; `upstream-shareware` requires them and embeds the specifically admitted shareware asset. The latter conflicts with M4's no-bundled-IWAD policy. [Makefile, lines 216–229](../engine/doom/Makefile#L216-L229) selects no embedded files, `DOOM_CONTROLLED_TITLE`, the controlled init/reachability inputs, and fixtures enabled by default. Do not use `--without-a1-fixtures` for the proven Worker: it needs diagnostic exports removed by that option ([inspector, lines 76–88](../scripts/inspect_doom.mjs#L76-L88)). Base build flags include `-g -Os` and reactor linking ([Makefile, lines 165–175](../engine/doom/Makefile#L165-L175)).
- [Build/closeout, lines 260–304](../scripts/build_doom.py#L260-L304) invokes only admitted `local-build`, produces `<out>/doom.wasm`, records its hash/length and typed static inspection in `<out>/evidence/manifest.json`, and reports `BUILD PASS` only after closeout. Source HEAD/status/local patch and focused configuration identities are recorded at [lines 157–175](../scripts/build_doom.py#L157-L175); logs/source evidence remain with engine output. The evidence pathspec deliberately retains the old source prefix as well as the new one to capture relocation deletions before commit, not to compile old sources. Failure/cancellation returns nonzero ([lines 329–344](../scripts/build_doom.py#L329-L344)). Static success does not establish engine runtime behavior.

The source visibly supports the intended trace-enabled, no-embed profile; reproducing the historical bytes or validating a fresh build with the Worker has **not** been performed. [doom-build.md, lines 24–50](doom-build.md#L24-L50) documents prerequisites and Make/Python ownership, but its later no-embed/interface limitations at lines 90–104 describe the older shareware baseline, not the current controlled-profile capabilities above. ## Worker and SDK packaging risks

[Controller, lines 361–363](../experiments/m3-e3/controller.js#L361-L363) creates a classic Blob Worker from four `.toString()` results. In [worker-boundary.js, lines 5–66](../experiments/m3-e3/worker-boundary.js#L5-L66), `i11VerifyStep` calls `i11MaskValid`; `i11Action` calls both helpers and admits integer durations 1–20. `titleWorker` owns WASM/import state and message dispatch; its [action path, lines 269–273](../experiments/m3-e3/worker-boundary.js#L269-L273) calls `i11Action` using the native single-tic export and observations.

A bundler can rename or alias identifiers or hoist transformation helpers outside a serialized function. `.toString()` captures function text, not its lexical environment; transformed references can therefore become unavailable inside the Blob. Disabling minification alone is not a preservation guarantee. No transformed failure was reproduced.

**Proposed minimal mitigation, not yet tested:** copy the existing boundary module into the app; import its untransformed text, for example with Vite raw-source import; remove only the explicit ESM export declaration at line 4 from the Blob payload; append the established `titleWorker()` invocation. Preserve all four function bodies, classic Blob Worker behavior, operation names, native step checks, serialized dispatch, and existing watchdog. Import normal module exports separately for main-thread validation. Check source preservation and actual built runtime behavior before claiming safety; do not redesign the engine or Worker protocol.

SDK transformation also needs verification. The installed `openai/internal/auth/x509-transport-state.mjs`, lines 1–5, imports both browser state and a `.js` adapter, selecting a fallback based on the Node export. The `.js` file guards CommonJS operations with `typeof module`/`typeof exports`. [M3-E2 README, lines 102–118](../experiments/m3-e2/README.md#L102-L118) records this mixed-module adapter and the accepted unbundled import. That does not prove Vite-transformed loading. Do not assume SDK patches, polyfills, or external runtime imports are needed; the credential-free built-output probe should resolve this uncertainty.
