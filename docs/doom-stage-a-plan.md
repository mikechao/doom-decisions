The default asset chain is unambiguous: `EMBEDDED_BINARY_FILES = DOOM1.WAD` (`A/Makefile:174`) adds generated C/header/object inputs to linking. The generator converts every byte to C array data (`utils/generate_code_for_embedded_file.py:23–46,85–116`). `A/src/doom_wasm.c:7,108–116` includes that header and copies the embedded array if the host supplies no WADs. At runtime, `wadSizes` writes count/total bytes, then `readWads` copies concatenated data and individual int32 lengths; first is IWAD, remaining files PWADs (`79–107`; header `105–161`). The adapter trusts these sizes. The bounded harness must validate them before initialization.

`E/src/d_main.c:1174–1202,1264–1268` obtains bytes, loads IWAD, identifies game, then adds PWADs. The browser example leaves both asset imports empty (`doom.html:88–90`), thereby choosing the embedded shareware. **Loading Freedoom at runtime does not remove embedded Doom bytes.** A different `EMBEDDED_BINARY_FILES` name alone also fails because the adapter hardcodes the header and symbols.

**A1:** adapter owns immutable controlled mode, single init/busy guard and temporary trace retrieval; WAT wraps WASI init. `d_main.c` keeps graphics/view setup but bypasses both implicit tic calls and scheduler baseline work in controlled mode. Perform only the first title-page preparation after setup, never attract playback. Central `NetUpdate` mode no-op and controlled nonblocking `D_Display` branch are needed immediately because A1 renders. Native builder/player/world/outer hooks record any accidental work from init onward. No ready-step or complete phase API yet.

**A2:** a narrow `g_game.c` whole-newgame preparation helper (phase-owned, zero tick) establishes one test map via normal `G_DeferedInitNew`/dispatcher, not direct JS struct mutation. This is the first shared dispatcher seam; extending it to budgeted chains waits for A3. Factor/reuse command installation plus normal level continuation inside `g_game.c`. `d_net.c` supplies a controlled callback/helper that installs the sole command without demo/preparation; `d_loop.c` owns a dedicated exact outer-tic path, bypassing TryRunTics/BuildNewTic/ring/TicdupSquash entirely. Step ordering: ready preflight -> M_Ticker once -> engine-owned minimal neutral/native input setup -> one `G_BuildTiccmd` -> saved command/tag -> final readiness/action/actor guard -> controlled installation/continuation -> P_PlayerThink entry guard -> completed P_Ticker -> ST/AM/HU continuation -> exactly one gametic/virtual increment -> return. No responders, mutable JS callbacks or preparation between build and entry. Initially neutral only; a test-only single native forward/turn binding is sufficient to make command/history and wait evidence nontrivial, without implementing Stage B's mask.

**A3:** `g_game.c` owns shared private helpers for rebirth, **one complete action dispatch**, command installation/specials/phase continuation, and state-change housekeeping. Legacy G_Ticker calls them in original order with its original unbounded dispatch semantics and no controlled budget. Controlled `advancePhase` alone runs preparation helpers; step refuses pending/reborn/title work and calls continuation only. Controlled housekeeping runs after each whole preparation unit and after a phase ticker/direct transition, before publication. Preserve legacy cleanup placement separately; moving it after every legacy action would change stock ordering.

Charge rebirth preparation, title advancement and action dispatch as complete units (normal experimental budget eight, test override one). Existing gameaction is continuation state; at most one private rebirth-prepared latch if needed to prevent reissuing G_DoReborn on resume while load is pending. No suspension inside load/restore, no action copy in adapter. Clear command validity before publication. Supported actions for the experiment: loadlevel, newgame, completed, victory, worlddone; whole loadgame barrier retained if internally reachable, but no public save/load feature. Suspended playdemo is not dispatchable PENDING; unknown/prohibited action is a real controlled-mode failure.

After preparation ran, return immediately with zero engine/world/playable counts, even if READY. Budget exhaustion with supported work remaining returns PENDING **after housekeeping**; resume only NONE. A permitted explicit non-playable phase tick uses phase-owned neutral/continue command, not native gameplay build; it increments outer/virtual once, may complete a dead world body, and returns before any newly requested dispatch. Live entry is always forbidden in phase, including menu viewz==1. Full menu, respawn, epoch and replay semantics remain Stage C; Stage A fixtures can request normal deferred actions and narrow phase pulses.

**Production necessities versus lab instrumentation:** retained controlled readiness/mode/reentry guards, final pre-P_Ticker/entry checks, actual build/entry/completion/outer accounting, and fail-before-body behavior must not depend on debug `assert` being enabled. Native command fields and local actor identity must match before consumption. Stage A implements only checks needed for its supported minimal command/profile. Test-only bounded trace, internal snapshots/digests, budget override, deferred-action injection and hang/trap fixtures use a compile define and test allowlist; production exports must omit them. No public full-command/mask/health API or 12-word layout in Stage A. Rich diagnostics cannot be used as a claim of Stage B delivery correctness.

Sequence design remains admission-only: if an experimental request number is used, spend it after all ready/neutral checks, before the stateful build; an interrupted build stays spent, a zero-work rejection does not. It is sufficient to trace that boundary privately; the full durable epoch/high-water protocol belongs to B/C.
