Propose `experiments/stage-a/harness.html` with WASM/IWAD file selectors, a classic Blob Worker, Canvas and downloadable bounded JSON results. Transfer selected bytes; Worker hashes the **final copied** WASM and externally supplied `assets/freedoom-0.13.0/freedoom1.wad` (28,795,076 bytes; SHA-256 `7323bcc168c5a45ff10749b339960e98314740a734c30d4b9f3337001f9e703d`). Hash mismatch fails before init. No fetch/server/package dependency is required. Actual file-page/Worker/hash behavior remains a Chrome check.

The retained baseline has ten function imports, typed in `scripts/inspect_doom.mjs:56–66`: `console.on{Error,Info}Message(i32,i32)`, `loading.onGameInit(i32,i32)`, `wadSizes(i32,i32)`, `readWads(i32,i32)`, `ui.drawFrame(i32)` return void; `gameSaving.writeSaveGame(i32,i32,i32)`, `readSaveGame(i32,i32)`, `sizeOfSaveGame(i32)` return i32; `runtimeControl.timeInMilliseconds()` returns i64. Final baseline exports are memory, `initGame()/tickGame()` returning void, `reportKeyDown/Up(i32)` returning void and fourteen immutable i32 key globals. WASI trampoline merge resolves the five preview1 imports internally; no external WASI shim is indicated. Controlled transformations may remove application imports: explain each change and pin an exact controlled inventory rather than accepting arbitrary imports.

Implement only retained imports: bounded copied logs, zero-return save stubs, fixed BigInt clock, dimensions assertion, and WAD delivery. `wadSizes` writes count=1 and total into checked four-byte little-endian slots; `readWads` copies admitted bytes and writes the single exact length. Refresh views from current `memory.buffer` on every callback, including after allocations/growth; validate unsigned pointer spans without wrapping.

Framebuffer path is `D_PageDrawer → I_VideoBuffer → I_FinishUpdate → DG_ScreenBuffer → DG_DrawFrame → ui.drawFrame` (`i_video.c:169–223,237–286,305–328`; adapter:121). Dimensions are **640×400, 1,024,000 BGRA bytes**, scaled 2× from 320×200. Immediately copy checked bytes to owned RGBA, swap B/R, set alpha=255 (palette alpha is zero; browser example:42–62). Hold one pending frame and publish only after successful render return; transfer that owned buffer to main thread for `putImageData`. Never transfer WASM memory. A frame proves visibility, not zero tics.

## Minimal implementation order and verification

1. **First falsifying experiment, after authorization:** implement the table's no-embed/init/render/time seams and counters together, build once through the full graph into fresh ignored output, inspect it, then instantiate those exact bytes in one Worker. Likely edits are the table's files, `src/doom_wasm.h`, new controlled WAT/root graphs and only necessary private hook declarations. Capture pre-init counters, init, post-init snapshot, one render and snapshot under fixed zero time with an already armed watchdog. Failure to return with visible TITLEPIC and zeros disproves the next assumption; diagnose locally, never prime a neutral tic. No preliminary baseline rebuild is needed.
2. Extend the same harness to five serialized render/snapshot pairs, a two-second main-thread idle delay with no Worker engine calls, then another render/snapshot. Preserve cumulative counters from before init. Assert zero native builds/player entries/world completions/outer tics at every boundary, unchanged `gametic`, `leveltime`, virtual time, one title preparation, no demo load, no scheduler/wipe/body entries. Snapshot copies observations only. Bounded traces, if used beyond counters, must flag overflow as evidence failure.
3. Separate missing-WAD Worker: deliberately supply count/total zero, bypassing host file admission to exercise C refusal. Require explicit error, engine-create=0, frame=0 and work counters=0. Set a **2-second main-thread timeout before each dispatch**, catch Worker errors/traps, terminate on timeout and reject late results. A Worker-local timer cannot interrupt synchronous WASM. Run separate test-only hang/trap cases with a 50 ms main heartbeat; require disposal/error within the following 250 ms, then fresh-Worker init/render success. Timeout is failure, never a successful engine receipt.
4. Complete the plan's acceptance evidence: two fresh completed trace/fixture builds and one fixture-disabled build; the first build counts only if it already contains the final accepted source/configuration. Retain final hashes/interfaces, build input/object inventories showing no generated WAD/header/object or embed link input, source/profile/root identities, Chrome version, frame screenshot/hash and cumulative observations. Verify fixture-disabled final exports exclude all test access/fixtures. Equal inventory is required; explain hash differences rather than assuming byte reproducibility.

Future commands: use the extended `python3 scripts/build_doom.py --profile controlled-title --out references/doom.wasm/build/<fresh-run> --jobs 2` (proposed interface, not runnable today), with its matching static inspector. Run documented build fixtures with live process integration disabled, `node --check scripts/inspect_doom.mjs`, and `git diff --check`. Inspect Make logs/dependencies for embed exclusion. Chrome manual checks above supply runtime acceptance; compilation, static export checks and nonblank pixels alone do not. Stop on unexplained imports, resource incompatibility, a hidden tic, fixed-clock hangs or a need for broad graphics/engine changes. DeHackEd remains disabled (`d_main.c:1204–1216`); title success says nothing about map compatibility.

## Decisions and boundary

No new asset/tool choice is needed. Recommend compile-time controlled mode, a small experimental init/render/status interface, and a local-file Blob Worker harness; reserve the public contract for later stages. The remaining owner action is separate implementation/build/browser authorization, including the plan's three acceptance builds and disposable fault cases. Runtime uncertainty, especially title graphics without a scheduler tic and Chrome operation latency, is an experiment gate, not something the owner must certify in advance.

**A1 only:** no gameplay stepping, A2/A3 lifecycle factoring, Decisions API, proxy, React/production UI, generalized Worker supervision or broad build-system rework. This investigation changed only this document; it did not recreate A0 scratch, run builds/tests/browser experiments, download/install anything, change Git state or publish artifacts.
